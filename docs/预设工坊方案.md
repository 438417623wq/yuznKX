## 一、四条硬勘察结论（决定方案可行性）

### 1.1 八槽位能直接映射到现有 identifier —— 不需要新数据模型

`Preset.prompts` 已经是完整的 SillyTavern Prompt Manager 模型，
每条 `PresetPrompt` 自带 `role` / `content` / `injectionPosition` /
`injectionDepth` / `injectionOrder` / `enabled` / `marker`。

思路文档里的八个部分**全部有现成落点**，见第三节映射表。

### 1.2 组装就是「按列表顺序铺消息」—— 顺序完全可控

`chat_provider._assemblePromptMessages()` 直接遍历 `preset.prompts`：

```dart
for (final prompt in prompts) {
  if (!prompt.enabled) continue;          // 禁用直接跳过
  if (prompt.identifier == 'chatHistory') { ...historyMarker... }
  ...
  addMessageEntry(role: normalizedRole, content: trimmed, ...);
}
```

- **`prompts` 的列表顺序 = 最终消息顺序**（这里不做排序）
- `injectionOrder` 只影响 `attach-existing` 类注入的排序，不影响相对位置槽位
- 所以「谁在前谁在后」由工坊生成时列表顺序决定 —— 这正是思路文档
  「先定 role 的位置与优先级」要的可控性

### 1.3 槽位内容是 `literal` **前置**到 `builtIn`

`_resolvePresetPromptContent()` 的收尾逻辑：

```dart
if (builtIn.isEmpty) return literal;
if (literal.isEmpty) return builtIn;
return '$literal\n\n$builtIn';
```

即：**预设自己写的文本排在该槽位内置内容的前面**。

| 槽位 | `builtIn` 来源 | 预设能做什么 |
|---|---|---|
| `worldInfoBefore` | 世界书（角色设定前） | 写开标签 / 板块标题，包住世界书 |
| `charDescription` | 角色卡 description | 同上 |
| `worldInfoAfter` | 世界书（角色设定后） | 写闭标签 / 补充说明 |
| `chatHistory` | 真实历史（marker） | **不能写内容**，只定位置 |
| `main` / `jailbreak` / `nsfw` / 自定义 | 无 | 纯自由文本 |

### 1.4 ⛔ 最危险的一条：预设存盘再读回会被**掺入 21 个默认 prompt**

`preset_provider._load()` → `Preset.fromJson()` → `parseWithReport()` →
`_mergeWithDefaultPromptManagerPrompts()`：

```dart
final merged = { for (final p in _defaultPromptManagerPrompts()) p.identifier: p };
for (final prompt in prompts) { ...覆盖同 identifier... }
return merged.values.toList();
```

**缺哪个 identifier 就补哪个，且默认 `enabled: true`。**

后果（如果工坊只写自己的槽位）：

1. `charPersonality` / `scenario` / `dialogueExamples` / `vectorsMemory`
   会被追加到**列表末尾** → 组装时排在破限槽位**之后**；
2. 不仅稀释底部注意力（思路文档明确说底部不要堆东西），
3. 更致命的是**最后一条消息不再是 assistant** → **prefill 直接失效**。

**对策（必须写进 packager）**：生成的预设把
`_defaultPromptOrderIdentifiers` 的 **21 个 identifier 全部显式列出**，
不要的写 `enabled: false`。这样 merge 时逐个命中、我的 `enabled` 生效，
`_applyPromptOrder` 也不会走到「无 order 项」那条分支，
最终顺序严格等于我给的列表顺序。

21 个 identifier（来自 `Preset._defaultPromptOrderIdentifiers`）：
```
worldInfoBefore, main, worldInfoAfter, charDescription, charPersonality,
scenario, personaDescription, nsfw, jailbreak, enhanceDefinitions, bias,
dialogueExamples, chatHistory, impersonate, quietPrompt, groupNudge,
summary, authorsNote, vectorsMemory, vectorsDataBank, smartContext
```

| 4 | 世界书（前） | `worldInfoBefore` | system | 引擎填世界书 |
| 5 | 角色设定 | `charDescription` | system | 引擎填卡 |
| 6 | 世界书（后） | `worldInfoAfter` | system | 引擎填世界书 |
| 7 | 历史前缀 | `ykxHistoryOpen` | user | `<game_save>` 开标签 |
| 8 | 聊天记录 | `chatHistory` | — | marker |
| 9 | 历史后缀 | `ykxHistoryClose` | **assistant** | `</game_save>` 闭标签 |
| 10 | 底部指令及重申 | `jailbreak` | **assistant** | 靠近底部的强注意力位 |
| 11 | 破限 / 伪造 COT | `nsfw` + `ykxFakeCot` | **assistant** | 末条 → prefill |

### 跨消息标签包裹历史（7–9 的实现手法）

思路文档要把聊天记录包进 `<game_save>【聊天记录】</game_save>`。
因为组装是「按顺序铺消息」，可以用**两条消息夹住历史**实现：

```
... prompt(7) 内容结尾是  "<game_save>"
... 真实历史若干条 ...
... prompt(9) 内容开头是  "</game_save>"
```

**引擎无需任何改动**，标签天然跨越历史消息。

> ⚠️ 不支持：文档里「二次包裹只留【最后一轮交互】」（`<checkpoints>`）。
> 那需要引擎侧把历史切片，本期不做。

## 三、八槽位 ↔ 思路文档对照

| 思路文档 | 本文槽位 | 备注 |
|---|---|---|
| 【重置（破限用）】 | 重置 | 消除渠道内置系统提示 |
| 【顶部声明】 | 顶部声明 | 文档拆的四块（破限加强 / 任务描述 / 角色分配与名词解释 / 附加指示）合并成一个槽位生成 |
| `<分割>` | 不单独设槽位 | 作为各槽位文本的**首尾标记**由 AI 生成，避免多一个空消息 |
| 【世界书（角色设定前）】 | 世界书（前） | = `worldInfoBefore` |
| 【角色设定】 | 角色设定 | = `charDescription`（可选叠加 `charPersonality` / `scenario`） |
| 【世界书（角色设定后）】 | 世界书（后） | = `worldInfoAfter` |
| 【聊天记录】 | 聊天记录 + 历史前缀/后缀 | marker + 跨消息标签 |
| 【底部指令及重申】 | 底部指令及重申 | = `jailbreak` |
| 【破限（破限用）】 | 破限 / 伪造 COT | = `nsfw` + 自定义 |

### 关于【破限】槽位

**做成用户自填 / 可留空。** 工坊负责**给位置、给结构、给顺序**，
不代写破限正文。两个理由：

1. 破限与渠道、模型强绑定 —— 思路文档自己也说这部分「经验主义、主观成分较重」，
   通用模板基本没用；
2. 我不会代写绕过模型安全策略的内容。

其余槽位（重置、顶部声明、角色分配与名词解释、文风/格式要求、
底部指令、诊断）**全部由工坊生成**。

## 四、数据模型

新增 `lib/features/preset_workshop/`，与 `character_workshop` 平行。

```dart
/// 工坊项目
class PresetProject {
  final String id;
  final String name;
  final DateTime createdAt;
  final DateTime updatedAt;
  final PresetStage stage;          // brief → structure → slots → diagnose → export
  final PresetBrief brief;          // 需求
  final PresetStructureKind structureKind;  // singleBlock / multiTurn
  final List<PresetSlot> slots;     // 槽位列表（顺序 = 消息顺序）
  final List<PresetDiagnosisIssue> issues;
  final String? exportedPresetId;   // 导出后写入的预设 id
  final List<PresetVersion> history; // 版本快照（限长 5，复用前端面板的做法）
}

/// 需求（向导第一屏）
class PresetBrief {
  final String rpMode;        // kp引导 / 小说模拟器 / 第一人称扮演 / 自定义
  final String targetChannel; // openai兼容 / claude / gemini / 本地
  final String pov;           // 第二人称 / 第三人称 / 第一人称
  final String language;      // zh-cn / en ...
  final int wordLimit;        // 建议输出字数
  final List<String> styleTags; // 文风标签（冷硬 / 华丽 / 轻小说 / 古典...）
  final int jailbreakLevel;   // 0 无 / 1 轻(role层) / 2 中(+顶部) / 3 重(+首尾)
  final bool wantCot;         // 是否要伪造 COT
  final String extraNotes;    // 自由补充
}

/// 槽位
class PresetSlot {
  final String key;           // identifier（默认槽位用引擎标识，自定义用 ykx* ）
  final String label;         // 中文名
  final String role;          // system / user / assistant
  final String content;
  final bool enabled;
  final bool isMarker;        // chatHistory
  final bool userOwned;       // true = 用户自填，AI 不覆盖（破限槽位）
  final bool locked;          // 结构锁定，AI 不可增删
  final String intent;        // 该槽位的设计意图（喂给 AI + 给用户看）
}
```

**存储**：Hive box `preset_projects`（照搬 `card_projects`）。
**导出**：转成 `Preset` 后走 `presetsProvider.save()`。

## 五、生成流程（五步）

### 步骤 1 · 需求对齐（`brief`）
向导式表单，把上表 `PresetBrief` 的维度逐项确认。
每个维度给「推荐值」，可一键「让 AI 帮我决定」（复用角色工坊的做法）。
渠道选择会**联动破限档位建议**：Gemini → 推荐「顶部破限、底部留给指令」；
本地模型 → 推荐低档位。

### 步骤 2 · 结构预览（`structure`）
按 `structureKind` 生成槽位骨架（第二节的表），显示成
**role + 槽位 + 顺序**的可视化列表。

- 可拖拽调序、可增删自定义槽位、可改 role
- 每个槽位显示「设计意图」（来自 `intent` 字段，也喂给 AI）
- **这一步是思路文档方法论的直接体现**：先定结构，再填提示词

### 步骤 3 · 逐槽位生成（`slots`）
一次请求返回「全部槽位的内容」（走 `_run()` 的 JSON 模式，
自带格式修复重试），然后：

- 每个槽位可**单独重生**（只把该槽位 + 上下文喂给 AI）
- 标 `userOwned` 的槽位 AI 不碰
- 标 `locked` 的槽位不参与增删

> 为什么一次请求而不是逐槽位请求：槽位之间有连贯性
> （顶部声明的任务名要出现在底部指令里），一次生成才能自洽。
> 单槽位重生用于局部不满意。

### 步骤 4 · 对话式微调（`slots` 续）
底部输入框「再说一句」，例如：

- 「顶部破限再强一点」→ AI 定位到相关槽位并改
- 「文风改成冷硬简洁」→ 改底部指令 + 顶部声明
- 「把世界书包裹的标签换成 `<world_setting>`」→ 改历史前缀/后缀 + 世界书槽位

**复用前端面板已验证的交互**：改动进「待确认」区 → 看 diff（`TextDiff`）→
应用/放弃 → 历史版本可回滚（限 5 版）。

### 步骤 5 · 诊断 + 导出
见下两节。

## 六、诊断（工坊内一步）

### 本地规则（0 token，自动跑）

**结构层 —— 这些是「静默出错」的高发区**

| # | 检查 | 级别 |
|---|---|---|
| 1 | `chatHistory` 数量 ≠ 1（0 次 = 历史无处插入；>1 次 = 历史重复） | 错误 |
| 2 | **缺少任一默认 identifier** → 存盘读回后被追加、prefill 失效 | 错误 |
| 3 | 多轮结构下末条 role 不是 `assistant` → prefill 失效 | 警告 |
| 4 | 连续同 role 消息 ≥ 3 条 → 部分渠道拒收 | 警告 |
| 5 | 全部槽位都被禁用 | 错误 |
| 6 | 自定义 identifier 与默认重名 | 警告 |

**内容层 —— 思路文档里明确提到的问题**

| # | 检查 | 级别 |
|---|---|---|
| 7 | 底部指令过长（>1200 字符）→ 文档：底部堆太多会让模型「变傻」 | 警告 |
| 8 | 单槽位过长（>3000 字符）→ 注意力稀释 | 提示 |
| 9 | 破限文本出现在 ≥3 个位置 → 文档：应逐步升级，不要一次上猛药 | 警告 |
| 10 | 分割标记风格不统一（同一预设里混用 markdown / xml / 自定义） | 提示 |
| 11 | 宏拼写：`{{char}}` / `{{user}}` 写错、未知宏 | 警告 |
| 12 | 槽位启用但内容为空 | 提示 |

**冲突层 —— 对应文档第五章「预设问题诊断」**

| # | 检查 | 级别 |
|---|---|---|
| 13 | 世界书槽位被禁用，但角色卡/全局世界书有启用项 → 世界书会另找位置插入，可能打乱结构 | 提示 |
| 14 | 预设内正则可能改写指令块 | 提示 |

### AI 复核（手动触发，省 token）
语义层检查：提示词歧义、自相矛盾、指令冲突、文风要求是否可执行。
要求只报**确定**的问题、最多 12 条（复用 `buildReview` 的做法）。

### 逐条修复
复用 P3 已落地的链路：
`buildIssueRepair` → `RepairDiffDialog.show()`（本地 LCS diff 预览）→ 应用 → 自动复检。

## 七、导出

1. **写入预设列表**：`PresetPackager.build(project)` → `Preset` → `presetsProvider.save()`
2. **可立即启用**：`activePresetIdProvider.setActive(id)`
3. **导出 JSON**：`Preset.toJson()`（酒馆格式），走文件导出
4. **导出前强制跑一次诊断**（错误级问题阻断，警告级提示）

`PresetPackager` 的职责就是把 `List<PresetSlot>` 转成
`List<PresetPrompt>`，并保证第一节 1.4 那条约束：
**21 个默认 identifier 全部列出**，未使用的 `enabled: false`。
